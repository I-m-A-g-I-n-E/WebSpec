# Deployment review findings

The reference deployments (`gateway/deploy/linux`, `gateway/deploy/macos`, `gateway/tools/setup-caddy.sh` and `docker/`) were reviewed against the deployment rules in `docs/spec/audit-deployment.md` before they were proposed. The first review found F1 to F56; the review after their fixes were merged found P1 to P20. Comments and tests cite many of them by these IDs; for the others, the code and tests describe the finding without naming it. The F1, F2, F4 and F10 that older comments in `gateway/webspec/app.py`, `handlers.py` and `pool.py` cite predate these reviews and are not these findings. This note is not normative (the spec is `docs/spec/`), and it gives no line numbers, because those in the original findings referred to code that has since changed.

## Contracts C1 to C4

The fixes agreed on four contracts between the parts, which comments also cite:

| ID | Contract |
|---|---|
| C1 | The gateway's listener. The gateway serves on a socket passed by systemd (`LISTEN_PID`, `LISTEN_FDS`: exactly fd 3), launchd (`WEBSPEC_LAUNCHD_SOCKET`) or the Docker init (`LISTEN_FDNAMES=webspec-init`), bound to loopback or to exactly the IP address `WEBSPEC_HOST` names. When it was asked to take a socket and cannot, it exits with status 3 and never binds the port itself; asked for none, it binds its own. |
| C2 | Caddy's listeners. `caddy-webspec.socket` passes 127.0.0.1:7001 as fd 3, 127.0.0.1:7003 as fd 4, [::1]:7001 as fd 5 and [::1]:7003 as fd 6. The gateway's site blocks bind fds 3 and 5, and direct sites bind fds 4 and 6. |
| C3 | A production host. A host is one exactly when `/etc/webspec/config.json` is a regular file. There, `webspec-ctl` edits `/etc/webspec/config.json` and `gateway.env`, and prints `Config: <path>`. |
| C4 | The guard-key file, read on every request. It is decoded as UTF-8 (a byte order mark removed), with whitespace and format characters around the key stripped. It must be one line of at least 16 characters, with no control or format character, at most 4096 bytes. |

## First review: F1 to F56

| ID | Severity | Where | Finding | Resolution |
|---|---|---|---|---|
| F1 | blocker | webspec-ctl (macOS) | `webspec-ctl` ran the first `caddy` on root's PATH, as root; macOS sudo keeps the operator's PATH, so anyone who could write a directory on it got root (DP-1, DP-4, GD-5). | Never looks `caddy` up on PATH; runs only a root-controlled binary, as user `caddy`. |
| F2 | major | Linux unit, macOS plist | The gateway bound 127.0.0.1:7002 itself, so the port was free on every restart; any local process could take it and receive Caddy's forwarded requests, signed headers included (DP-9). | `webspec-gateway.socket` (Linux) and launchd `Sockets` (macOS) hold 7002; the gateway takes the socket. |
| F3 | major | Linux units | `Restart=on-failure` treated SIGTERM and exit 0 as a clean stop, so a stdio server could stop the gateway for good and leave 7002 free (DP-7). | `Restart=always`; graceful shutdown is capped at 35 s, so a hung call cannot stall it. |
| F4 | major | Linux installer | The next steps said to edit `gateway.env` with sudoedit, which copies the file, guard key and secrets included, to a file the invoking user owns (DP-1, GD-5). | Next steps: edit as root with a fixed editor or append as root; never sudoedit. |
| F5 | major | Linux installer | `install.sh` ran an existing `/opt/webspec/venv/bin/python` as root without checking who owned the venv, so a user who could change it got root (DP-1, DP-4). | A venv another user can change is moved aside, never run, and rebuilt. |
| F6 | major | Linux installer | `install.sh` built the venv from `python3` without checking who could change it or its standard library; whoever could change them ran code as `webspec`, which reads the guard key (DP-1). | Refuses an interpreter, stdlib or libpython another user can change, unless `--allow-nonroot-python`. |
| F7 | major | Caddy setup | `setup-caddy.sh` ran Python and installed units from its checkout as root without checking who could change it; on the live host, the agent's user could (DP-4). | Refuses a checkout, venv or prebuilt `caddy` that a user other than root can change. |
| F8 | major | webspec-ctl | Direct sites (`add --direct`) were served on 127.0.0.1:7001, the port the agent must be allowed, so the agent reached their apps without the guard or audit log (DP-3). | Direct sites moved to a listener of their own, :7003, outside the agent's allow-list. |
| F9 | major | Caddy setup | Re-run as before on a dev host, `setup-caddy.sh` set every existing site block aside, took every route down, and reported success. | Plans first and refuses to serve fewer hosts unless `ALLOW_SHRINK=1`; compares each host after. |
| F10 | major | webspec-ctl | On the old Caddy layout, `webspec-ctl` wrote `fd/3 fd/4` blocks; the reload failed but the files stayed, so Caddy's next start failed and took every route down. | Refuses unmigrated layouts; validates a staged copy, and restores every file if the reload fails. |
| F11 | major | webspec-ctl | Without `WEBSPEC_DOMAIN`, which sudo drops, and with no `gateway.env` on a dev host, a routine `caddy-sync` silently removed every public address and reported success (DP-5). | The domain is recorded in the Caddyfile; dropping it needs `--no-public` or `WEBSPEC_DOMAIN=`. |
| F12 | major | Linux installer | `install.sh` overwrote a system `webspec-gateway.service` running the dev gateway as the login user, which kept running under the production unit's name until the next restart (DP-1, DP-4). | A foreign unit is backed up and refused; the installer checks MainPID runs as `webspec`. |
| F13 | major | macOS installer | `install_plist` copied the plist before `load_daemon`'s checks, and refusals neither disabled nor booted it out, so launchd loaded the refused daemon at the next boot (DP-1, DP-4, DP-7, GD-5). | Refused runs disable an unloaded job; a loaded one keeps running unless PATH is unsafe. |
| F14 | minor | Linux installer | `install.sh` kept the invoking environment, so under `sudo -E` the agent's `PIP_*` variables or `pip.conf` could point root's pip at an index the agent controls (DP-1). | As root, re-executes in a clean environment; overrides became options; pip runs `--isolated`. |
| F15 | minor | Linux and macOS installers | Both installers adopted an existing `webspec` or `_webspec` account even when it was a login account, so someone who could log in as it could read the guard key (DP-1). | Refuses a login-like account (password, shell, human UID, shared IDs) unless explicitly allowed. |
| F16 | minor | Linux installer | `install.sh` installed `config.example.json` as the live config, so a fresh gateway started with two placeholder services that could not work. | A fresh `config.json` has no servers; the example is installed beside it as a reference. |
| F17 | minor | Linux installer | `install.sh` enabled the unit even without a guard key, so the next boot started a keyless gateway that logged nothing until requests failed (GD-5). | Service enabled only with a key, and cannot start without one; gateway warns at startup. |
| F18 | minor | Linux installer | `install.sh` reused an existing venv without checking it, so after a distribution upgrade changed Python the unit failed and re-running the installer could not repair it. | A stale venv is rebuilt; the old one is put back if the rebuild fails. |
| F19 | minor | Linux installer | The Linux install path claimed DP-1 to DP-8 and never told the operator that confining the agent's egress was theirs to do (DP-3). | Header lists the rules it sets up; next steps say DP-3 is the operator's job. |
| F20 | minor | gateway, webspec-ctl | An empty `WEBSPEC_HOST` made the gateway listen on every interface, and `webspec-ctl add --secret WEBSPEC_HOST` could append exactly that line to `gateway.env` (DP-8). | Empty `WEBSPEC_HOST` means loopback; `--secret` and `--clean-env` refuse `WEBSPEC_*` names. |
| F21 | minor | gateway | A 404 for an unknown destination on the public domain listed every service name, level-0 ones included, which are kept off the public domain (HG-7). | Public-host 404s no longer list services; the bare-domain index stays an open question. |
| F22 | minor | gateway | Without a guard key, requests that need it got a plain 500 but no audit entry, and each logged a full traceback, about 7 KB (AU-1). | Such requests are audited (reason `guard_key_unavailable`) and log one line, no traceback. |
| F23 | minor | gateway | Reading `WEBSPEC_GUARD_KEY_FILE` kept a UTF-8 BOM and other invisible characters, so a BOM broke a good key and a BOM-only file gave a publicly computable key (GD-5). | Decodes `utf-8-sig`, strips invisible characters, refuses empty, multi-line or under-16-character keys. |
| F24 | minor | registry | `docker/README.md` had `webspec_registry` run as the agent's user with the guard key, and it dialed by name, so a `[::1]` listener got its guard tags (DP-1). | Registry dials by IP and harvests guarded services only on opt-in; README withholds the key. |
| F25 | minor | Caddy config (Linux) | Caddy's log filter stripped only the query, so an absolute-form target such as `http://user:pass@svc.localhost/` logged its password (DP-6). | The URI filter also strips the scheme, authority and userinfo. |
| F26 | minor | webspec-ctl | `webspec-ctl` chose Caddy's sockets by asking the kernel about IPv6, so a later IPv6 change left blocks binding sockets systemd never passed: Caddy could not start (DP-9). | Sockets come from the installed socket unit, recorded in the Caddyfile; a mismatch is refused. |
| F27 | minor | Caddy setup | `setup-caddy.sh` did not warn that the old setup's journal held unfiltered Caddy entries (query strings, guard and clearance headers) readable by adm and systemd-journal members (DP-6). | Replacing an earlier setup now warns about those entries and how to drop them. |
| F28 | minor | Caddy config (Linux) | Rate limits keyed IPv6 clients by full address, not /64, and exempted `/__nonce` and `/__challenge`, so one public client could append audit entries at line rate. | IPv6 clients count by /64; nonce paths have zones of their own instead of exemption. |
| F29 | minor | Caddy setup | `setup-caddy.sh` stopped the old Caddy before systemd bound :7001, so a process that took the port in that gap received the tunnel's traffic (DP-9). | Stops cloudflared while the ports change hands; restarts it only once systemd holds every listener. |
| F30 | minor | Caddy setup | The migration set legacy direct-site blocks aside instead of regenerating them, printed a recreate hint that failed on the host, and overwrote the old unit without a backup. | Legacy direct sites are regenerated on :7003; a replaced custom unit is backed up. |
| F31 | minor | Caddy setup | The advice to set `WEBSPEC_DOMAIN` and re-run never said to restart the gateway, which reads it only at startup, so new public hosts got 404. | Advice names where this host's gateway reads the domain, and the restart it needs. |
| F32 | minor | webspec-ctl | Health probes dialed `<name>.localhost` by name: stock Debian could not resolve it, and elsewhere ::1 came first, where any local user could answer root's probe. | Probes connect to 127.0.0.1 and send the Host header explicitly. |
| F33 | minor | webspec-ctl | `webspec-ctl health` read `~/.claude.json` instead of `/etc/webspec/config.json`, so on a production host it reported every service as not found. | `health` uses the same config file as every other command, and prints it. |
| F34 | minor | webspec-ctl | `webspec-ctl add` took the guard from `--guard`, not the level, so `--level 0` got a guarded public block and the printed Guard could contradict the level. | The level decides guard, URL and block; `--level 0` means no guard. |
| F35 | minor | webspec-ctl | `--type` defaulted to `http`, so `webspec-ctl add NAME --command ...` failed and wrote nothing. | `--command` alone means stdio; `--url` or `--port` means http. |
| F36 | minor | webspec-ctl | `webspec-ctl` switched to `/etc/webspec/*` once that directory existed, so `rm` on a dev host could report success while the gateway kept serving the service (DP-4). | Production means `/etc/webspec/config.json` exists; every command prints the config it uses. |
| F37 | minor | webspec-ctl (macOS) | `webspec-ctl` edited the macOS `gateway.env`, which the daemon sources as shell, as a systemd file: export lines were missed, so secrets were blanked or survived removal. | Matches export lines; names must be shell identifiers; reports Removed only after a removal. |
| F38 | minor | Docker stack | Neither container had a restart policy, so a gateway exit, OOM kill, daemon restart or reboot left the stack down until someone restarted it (DP-7). | `restart: unless-stopped` on both services; a README section covers restarts. |
| F39 | minor | Docker stack | Stdio servers ran with HOME on the persistent state volume and without `PYTHONNOUSERSITE`, so one server's planted `.pth` ran in every Python server, surviving rebuilds (DP-4). | Stdio servers of a gateway run with `-I` get `PYTHONNOUSERSITE=1`; README explains the risk. |
| F40 | minor | Docker stack | The config was a single-file bind mount, so an edit that replaced the file (`webspec-ctl`, `sed -i`) never reached the running gateway (DP-4). | Config is a read-only directory mount, so edits that replace the file reach the gateway. |
| F41 | minor | Docker README | The README's `audit()` helper always passed `docker run -i`, so in a script fed on stdin the first call swallowed the rest and later steps silently never ran (AU-3, AU-4). | `audit()` drops `-i`; a separate `audit_stdin()` serves the one heredoc check. |
| F42 | minor | Docker README | The README's demo config left out `FASTMCP_CHECK_FOR_UPDATES=off`, which the same README recommends, so the demo server contacted PyPI at startup (DP-3). | The demo entry sets `FASTMCP_CHECK_FOR_UPDATES=off` and `PYTHONNOUSERSITE=1`. |
| F43 | minor | Docker stack | Caddy was published on 127.0.0.1:7001 only, leaving `[::1]:7001` to any local user; clients that try ::1 first sent it guard tags and GET arguments (DP-3, DP-5, DP-8). | Also published on `[::1]:7001`; the README says when Docker does not hold it. |
| F44 | minor | Docker Caddyfile | The Docker Caddyfile forwarded `*.localhost` even with Cf-Ray, so if a tunnel rewrote Host to a loopback name, public requests reached level-0 tools without the guard (DP-5). | A tunneled request for a loopback host now gets 421, as on bare metal. |
| F45 | minor | Docker Caddyfile | The Docker Caddyfile did not pin HTTP/1.1, so Caddy served h2c on :7001, a wider surface than bare metal, though no Host bypass was found. | Pins `protocols h1`, as on bare metal. |
| F46 | minor | macOS installer | `check_env_file` warned about `gateway.env` settings that widen exposure but not `WEBSPEC_CORS_ORIGINS`, which lets other origins read answers and send unsafe methods (DP-8). | Warns on `WEBSPEC_CORS_ORIGINS` by name, read from `gateway.env` as the daemon sources it. |
| F47 | minor | macOS installer | The `gateway.env` PATH check judged a symlink's final file only, so a target in a writable directory, or a dangling link, could be replaced (DP-1, DP-4). | Each hop of a link chain is checked; a dangling link counts as unsafe. |
| F48 | minor | macOS installer | `check_dev_agent` looked only at `SUDO_USER`'s domains, so from an admin account a dev gateway loaded for the agent's user, on port 7001, went undetected (DP-1, DP-7). | Checks every login user's agents and plists; a gateway on 7001 holds the daemon back. |
| F49 | minor | macOS installer, webspec-ctl | macOS shipped no proxy and `webspec-ctl`'s Caddy management could not work there, so those rules rested on a proxy the operator built by hand (DP-5, DP-6). | Documented limit: no macOS proxy; `webspec-ctl` skips Caddy there; next steps specify one. |
| F50 | minor | macOS installer | The documented key fill (`op read` piped to `sudo tee`) emptied `guard.key` when `op read` failed, and the gateway re-reads it per request, so every guarded request failed (GD-5). | `install.sh --fill-key` replaces `guard.key` atomically, and only with a key the gateway accepts. |
| F51 | minor | macOS installer | `guard.key` was `_webspec:_webspec` 0400, so any stdio server, running as `_webspec`, could rewrite or blank the key the gateway re-reads on every request. | `guard.key` is `root:_webspec` 0440, and stray ACLs are removed. |
| F52 | minor | tests | A macOS link test lacked `@non_root` and failed whenever the suite ran as root, as in a root container. | The link tests no longer depend on the runner's UID. |
| F53 | minor | tests | F52's test passed even with `-L` removed from `unsafe_entry`, so a regression in the link-following that refuses swappable stdio binaries went unnoticed (DP-1, GD-5). | The test asserts the exact link message; link-following is now an explicit walk. |
| F54 | minor | CI | CI never set `WEBSPEC_TEST_CADDY`, so the only test that ran the generated config through a real Caddy always skipped, and a config Caddy rejects would merge green (DP-5, DP-6). | CI builds the pinned Caddy and fails unless the real-Caddy tests run and pass. |
| F55 | minor | CI | The docs job ran only `test_docs_consistency.py`, so `test_rendering.py`, which checks that each rule renders as its own list item, never ran. | The docs job runs all of `docs/tests` and fails on any skip. |
| F56 | minor | tests | `test_deploy_macos.py`'s docstring called the guard-key-file tests expected failures, though they passed, which could mislead someone triaging a real failure. | The sentence was deleted. |

## Second review: P1 to P20

| ID | Severity | Where | Finding | Resolution |
|---|---|---|---|---|
| P1 | major | Docker init | `docker/init.py` let go of port 7002 as soon as the gateway exited, while other container processes still ran, so a leftover could bind it and receive forwarded requests (DP-9). | Contested: verifiers split on reproducing it. Fixed: the init kills other processes before releasing 7002. |
| P2 | major | Linux Caddy units | A Caddyfile written with IPv6 bound `fd/5` and `fd/6`; after a boot with `ipv6.disable=1` systemd passed fewer sockets, so Caddy crash-looped and the public path stayed down (DP-9). | `ExecStartPre` names the IPv6 change; `setup-caddy.sh` no longer writes the IPv4-only drop-in; health reports mismatches. |
| P3 | minor | gateway | A valid-JSON config that was not a valid registry was dropped silently on reload, revocations included, and never retried; at the next start the gateway crash-looped (DP-4). | Rejected with one warning; the gateway keeps its last good registry, empty at startup. |
| P4 | minor | Docker stack | On an IPv6-enabled compose network nothing held `[::]:7002`, so a uid-10001 process could listen there and receive what Caddy sent over IPv6 (DP-9). | Compose pins the network IPv4-only; the init also holds `[::]:7002` without listening. |
| P5 | minor | Caddy config (Linux) | Rate-limit zones trusted the client-sent Cf-Ray and Cf-Connecting-Ip, so a local process could escape the local cap or spend a chosen public client's allowance. | Documented limit: comments now state what the zones guarantee; no redesign. |
| P6 | minor | Linux installer | The F6 check judged stdlib links by owner and skipped site directories, so code root's `python3 -I` runs, such as Debian's `sitecustomize.py` target, went unchecked (DP-1, DP-4). | Follows links hop by hop; runs base Python with `-I -S`; warns on site directories. |
| P7 | minor | macOS installer | `check_caddy_port` recognized a second gateway on 7001 only by `-m webspec` in its command line, so other launch forms got only a warning (DP-1, DP-7). | Refuted: documented launch forms are all caught; refusing would not change who gets 7001's traffic. |
| P8 | minor | Linux unit and installer | The unit's and installer's key checks accepted a key of invisible characters only, such as U+200B, which the gateway treats as no key, then reported a started gateway (GD-5). | Unit sets `WEBSPEC_REQUIRE_GUARD_KEY=1`: no usable key, exit 3. Installer applies the gateway's rule. |
| P9 | minor | Docker init, gateway | The init bound a `WEBSPEC_HOST` host name that the gateway, which accepts only IP literals, then refused, so the container crash-looped; its error named systemd as the holder (DP-8). | The init refuses a `WEBSPEC_HOST` that is not an IP; messages name the real holder. |
| P10 | minor | webspec-ctl, Caddy setup | When a gateway service took a direct site's name, `add` replaced it silently and `caddy-sync` advised a cloudflared rule to :7003 that broke the host (DP-3). | `add` refuses a direct site's name without `--force`; `caddy-sync` reports the move's real direction. |
| P11 | minor | webspec-ctl, Caddy setup | On Linux, `webspec-ctl` and `setup-caddy.sh` honored `export WEBSPEC_DOMAIN=` lines in `gateway.env`, which systemd ignores, so Caddy served a domain the gateway never got (DP-5). | Values in files systemd reads come from `KEY=` lines only; export lines draw a warning. |
| P12 | minor | webspec-ctl | `add --direct` accepted Caddy's listeners and the gateway's port as the upstream; a direct site pointing at :7003 looped each request through Caddy about 500 times, ending in 431. | `add --direct` refuses 7001, 7003 and the gateway's port as an upstream. |
| P13 | minor | webspec-ctl | Health checks counted only statuses below 400 as up, so every guarded service, which answers 401 to an unsigned probe, showed as down or unreachable. | 401 and 403 count as reachable, shown as `ok (guarded)`. |
| P14 | minor | gateway (macOS) | An unknown launchd socket name was logged as "this process is not a launchd job" (launchd answers ESRCH, not ENOENT); the gateway still exited without binding (DP-9). | Filed as refuted with no verifier vote. Fixed anyway: the ESRCH message names both causes. |
| P15 | minor | docs and messages | Under Docker the gateway logged that its socket stays bound while it restarts, which Docker never does; the spec's environment table missed two variables; a `config_writer` comment was stale. | Log line now fits the holder; the spec's table lists both variables; comment corrected. |
| P16 | minor | CI | The CI gate required only tests named `test_real_caddy`, so the ten real-Caddy tests in `test_caddy_limits.py` could all skip while CI stayed green (DP-5, DP-6). | The gate requires every real-Caddy module by name; a static test keeps the list complete. |
| P17 | minor | tests | Eight tests in `test_deploy_linux.py` failed as root: three assumed their files were another user's, and five compared plans made with different PATHs. | As root, fixtures are given to UID 65534; plan tests use root's PATH. |
| P18 | minor | tests | Run in-process as root, `webspec-ctl`'s `main()` set PATH to a fixed safe value for the rest of the session, so root test results depended on test order. | `conftest.py` restores PATH after every test. |
| P19 | minor | tests | On Python 3.13 the init's signal test failed: `posix_spawn` left glibc's signals 32 and 33 ignored in the child, though the deployment was unaffected. | The test starts the init by fork and exec; CI's 3.13 leg cannot reproduce it. |
| P20 | minor | tests | Six activation tests of the `WEBSPEC_HOST` address rule were skipped on macOS, citing the firewall, though they ran and passed there (DP-8). | Refuted: the skip is deliberate and documented, and Linux CI runs these tests. |
